Execução nativa isolada por Action.

SandboxActor é a camada Linux leve para executar módulos de Action não confiáveis ou semi-confiáveis fora do espaço de memória privilegiado do Runtime.

Landlockseccompcgroup v2rlimitsno_new_privsCommit Barrier
01 · Propósito

Um boundary executável entre Runtime e código nativo.

Quando o sandbox está habilitado, o módulo nativo não é carregado diretamente pelo Runtime. Ele roda em um worker separado, com política autorizada pelo host e controles instalados antes do dlopen.

01

Isolamento de memória

O módulo não compartilha heap, stack, secrets ou bibliotecas do Runtime privilegiado.

02

Capabilities explícitas

O manifest solicita direitos. A política do host continua sendo a autoridade que pode concedê-los.

03

Fail closed

Quando um mecanismo obrigatório de enforcement não está disponível, a execução não degrada silenciosamente.

02 · Modelo de execução

Controles entram antes do código da Action.

Runtime → lê o Action manifest → valida policy request contra o policy ceiling do host → cria SandboxActor worker → PR_SET_NO_NEW_PRIVS → rlimits / cgroup v2 → Landlock filesystem domain → network policy hook → seccomp → dlopen(Action module) → execute → serialize required state → commit barrier → Runtime emite .Ok / .Error → zeroize transient memory → exit
03 · Segurança

Princípios que não dependem de Docker ou microVM.

Filesystem

Action tree read/execute por padrão. Escrita somente em áreas explicitamente declaradas, como tmp/state.

Processos

Spawn negado por padrão. O worker roda sem privilégios adicionais e com syscall boundary via seccomp.

Rede

Allow-list pode ser declarada no manifest. Enforcement de produção deve usar namespace/eBPF/cgroup controller ou equivalente.

Hardening

PR_SET_NO_NEW_PRIVS é ativado antes de carregar código não confiável.

Healers também isolados

CodeHealer recebe escrita apenas no implementation.zig; SystemHealer apenas no caminho de configuração autorizado.

Permissões estáveis

Evita chmod dinâmico por execução e as janelas de race causadas por segurança global mutável.

04 · Resource Budgets

Uso de recursos é parte do contrato de execução.

Limites podem ser derivados dos Semantic AtomicBehavior Types e medidos pelo cenário MaximumValidPayload.

Bounds semânticos

  • max_chars / max_bytes
  • max_items / max_depth / max_properties
  • max_digits / max_scale
  • rejeição no Gateway antes de alocar estado da Action

Testes de fronteira gerados

  • min-1, min, min+1
  • max-1, max, max+1
  • tipo primitivo incorreto
  • encoding/estrutura inválidos
  • MaximumValidPayload
05 · Autoridade terminal

Sandbox executa. Runtime decide o terminal.

O SandboxActor fornece primitives de commit barrier e serialização, mas a emissão canônica de .Ok/.Error permanece responsabilidade do Runtime que o incorpora.

execute → serialize required Agent memory → validate → persist/cache required state → COMMIT BARRIER → Runtime emite .Ok → zeroize transient arena → release falha de commit → Runtime emite .Error
06 · Integração A³

Action → Actor/SandboxActor → Supervisor → Dynamic Module.

Responsabilidades do Runtime

  • autorizar capabilities;
  • resolver requests do manifest contra o policy ceiling;
  • delegar cgroup v2 quando necessário;
  • instalar enforcement de rede;
  • controlar persistence/cache;
  • emitir eventos terminais canônicos;
  • fornecer semantic bounds.

Responsabilidades do SandboxActor

  • no-new-privileges;
  • Landlock;
  • rlimits e cgroup v2;
  • seccomp;
  • isolated module loading;
  • zeroization;
  • resource budgets;
  • commit-barrier e equivalence-key primitives.
